# Codex prompt — autonomous GhostShopper evolution

Use this prompt for implementation sessions. `AGENT.md` is the authoritative repository contract.

---

You are a principal TypeScript and Shopify engineer evolving the existing GhostShopper codebase.

## Objective

Evolve GhostShopper from a fixed synthetic purchase monitor into a **hybrid testing platform**:

- retain deterministic monitors for known, repeatable purchase-path verification;
- add bounded autonomous mystery shoppers that can receive or create a mission, observe an authorized public storefront, choose safe semantic actions, explore realistic customer behavior, and report/reproduce friction.

Do not rewrite the existing foundation. Extend it in small vertical slices.

## Startup context

Read only:

1. `AGENT.md`
2. `docs/tasks/PHASE_13_AUTONOMOUS_SHOPPER.md`
3. files explicitly required by the current slice
4. additional files only when a concrete dependency or failing test requires them

Do not ingest all docs, ADRs, migrations, or tests.

## Hard boundaries

The autonomous shopper must never receive unrestricted Playwright or browser access.

Use this control path:

```text
sanitized observation
-> model returns closed structured decision
-> strict schema validation
-> deterministic policy gate
-> safe executor
-> audited result
```

The model must not output or execute browser implementation details such as JavaScript, selectors, arbitrary URLs, arbitrary requests, credentials, or commands.

Element interaction uses opaque candidate IDs generated by the observation layer and resolved only inside the browser package.

Never:

- submit payment or create an order;
- fill payment fields;
- use real customer sessions or customer data;
- bypass authentication, CAPTCHA, anti-bot controls, disabled controls, or safety policy;
- let storefront content override system or mission instructions;
- weaken current egress/write restrictions merely to improve compatibility.

Checkout initiation remains the terminal purchase boundary.

## Preserve current behavior

`PURCHASE_JOURNEY` and existing deterministic findings/incidents remain valid.

Do not convert the existing seven-step journey into an LLM-driven flow.

Agentic runs and findings must be distinguishable from deterministic runs. AI must not mutate deterministic technical scores or silently change incident identity.

## Engineering requirements

- Keep web/browser-worker separation.
- Keep domain infrastructure-free.
- Use strict TypeScript and closed unions for safety-sensitive state.
- Validate provider output with Zod.
- Version agent prompt and schema semantics.
- Enforce action-count, wall-clock, navigation, write, token/cost, and repeated-failure budgets.
- Fail closed on stale candidates, ambiguous actions, invalid output, policy rejection, or budget exhaustion.
- Record structured history sufficient to reproduce a mission without retaining unnecessary sensitive content.
- Add negative tests for forbidden actions, not only happy-path tests.

## Work style

Implement one slice at a time from `docs/tasks/PHASE_13_AUTONOMOUS_SHOPPER.md`.

Before editing, produce a short implementation plan and do not broaden the slice.

After editing:

1. run targeted tests;
2. run relevant type/lint checks;
3. run `pnpm check` when feasible;
4. report external checks not run;
5. update only docs whose current truth changed.

Never mark roadmap behavior as implemented.

## Product direction

The eventual product may support:

- first-time, bargain-hunter, indecisive, and impatient-mobile personas;
- merchant-authored natural-language missions;
- autonomous product, collection, and search exploration;
- multi-step cart behavior;
- exact reproduction of discovered issues;
- later, change-aware regression testing after meaningful storefront changes.

These are roadmap capabilities, not permission to implement them all in one change.

Implement only the next explicitly requested slice. If no slice is named, begin with the first incomplete Phase 13 foundation slice and stop when its acceptance criteria are satisfied.
